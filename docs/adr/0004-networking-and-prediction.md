# ADR 0004: Replication through an adapter, interest on the region grid, prediction corrected against exact acks, and a world that does not pause

Status: accepted, 2026-09-12.

## Context

Phase 4 put a player in the simulation, a dedicated server in front of it and a menu over it, and every one of those raised a networking decision. The port in `strata-net` had been drawn in Phase 0 with nothing behind it (ADR 0001: authority is a port, networked authority is an adapter in a later crate). The questions were which library to put behind it, how a server with a world tens of kilometres across decides what each client is told, how far the client is allowed to run ahead of the server for its own character, and what a pause means in a world that other people are standing in.

## Options

**The replication library.** Write our own over a UDP transport, or take one of the Bevy crates. `bevy_replicon` was the only one at Bevy 0.19 with server-authoritative component replication, client and server events, a per-client visibility mask, a test backend that runs two apps in one process without a socket, and a transport split (`bevy_replicon_renet` over renet's netcode) that leaves the sim crates with no socket code at all. Writing our own would have been the byte framing, the reliability and the change detection that replicon already has, before any of the game's decisions came up.

**Interest management.** A radius per client, a grid of cells sized for the purpose, or the region quadtree the streamer already walks. The radius is a distance check per entity per client per tick and knows nothing about what the client has loaded. A separate grid is the region grid again with another size to tune. The quadtree is what the client's own streaming uses (ADR 0003 promised the region grid would double as the server's interest unit), and its selection carries the hysteresis a boundary needs.

**Prediction.** No prediction (the local character moves when the server says so, a round trip after the key), a snap to the server's position when the prediction is wrong, or full reconciliation (rewind to the server's acked state and replay the unacked inputs through the physics). No prediction is unplayable over anything but a LAN. Full reconciliation needs the character step callable outside the schedule for several ticks in a row, which the physics crate does not offer yet.

**Pause.** Stop the simulation while a menu is open, or leave it running and only take the keys and the mouse away from the game.

## Decision

1. **`bevy_replicon` is the adapter, behind the port.** `strata-net` keeps the vocabulary every crate uses: `NetRole` (standalone, server, client), `Replicated` (mark an entity for the wire), `NetStatus` (what the wire is doing, for a HUD). `strata-net-replicon` maps it onto replicon: the server turns `Replicated` into replicon's marker, a client's `PlayerIntent` becomes a numbered client event, the sim clock rides on a replicated singleton entity, and a `Welcome` event names the client's player and the server's seed. The crate sits above the physics (the server spawns a `CharacterController` per client) and below the render crates; it is behind the facade's `net-replicon` feature so a build that neither serves nor connects carries no transport, and `just server-check` holds the server binary's graph to no render, window, UI or text crate. The registration of what crosses the wire is one function both roles call, because replicon hashes the registration order into the protocol id.

2. **Interest management is the region grid.** The server runs the streamer's own `Selector` once per client from that client's player, walked again when the player has moved eight metres, and an entity with a position is visible to the client when the selected region containing it is at LOD 2 or finer: about 1.3 km with the default streamer, the distance at which a walking player's terrain is fine enough to stand another player on. The decision is a pure function (`in_interest`) and the bit is set through replicon's `ClientVisibility` before replication sends, so a client authorized this frame never receives an entity outside its interest. Out of interest an entity is despawned on the client and respawned when it returns.

3. **Prediction is a correction against exact acks, for now.** The client's own player carries the same `CharacterController` the server steps it with, so the same physics moves it the moment a key goes down. Every intent the client sends carries a sequence number; the server applies one per tick in order and echoes the sequence it applied on the player with the position. When no intent has arrived for a tick the server holds the player still and leaves the ack where it was, rather than running the last intent on under an ack that did not move: the position it reports for a sequence is then always the one that sequence produced, whatever the wire did. The client keeps the position it predicted after each sequence and compares the server's position for an acked sequence with the prediction for that same sequence, never with "now". Over half a metre of disagreement the player and every prediction still on record are shifted by the difference. A shift and not a set, because the server's position is several ticks old: setting the player to it rewinds those ticks, the next ack then disagrees by exactly what was rewound, and one correction while walking becomes one every few ticks for the rest of the walk (a review of the first version found sixty in a twelve-second walk). That is exact rather than latency-guessing, it needs no clock synchronisation, and the two-client tests show it tracking within the queue's lag over a sprint, absorbing a two-tick stall with no correction, taking exactly one correction for a six-tick stall (the queue drops the oldest intents, so the paths really diverged) and one for a 30 m error while sprinting. What it is not is reconciliation: a correction is visible as a hitch. Real reconciliation needs (a) `CharacterController::step` runnable outside the schedule with a spatial query over the colliders of the rewind position (it is a plain method already; the `MoveAndSlide` system parameter is what ties it to a system), (b) the client keeping its intents until acked, and (c) a rewind of the local player to the acked server state followed by a replay of the later intents in one frame. The ground streams in around the player, so the colliders are there; the callable step is the missing piece.

4. **The simulation does not pause under the menu.** This is an MMO: other players are in the world, and on a client the world is the server's anyway. A page or modal on the slotted screen stack releases the cursor, stops the steering systems (flycam, orbit, WASD into `PlayerIntent`) and clears the local player's intent, so the keys the menu is reading never also walk the character and a W held when the menu opened does not walk it into the sea. Everything else runs: the clock, the streamer, the physics, replication. On a connected client the cleared intent is what the next tick consumes and sends, so the server's copy of the player stops too, one round trip later, and a player who leaves the menu open on a cliff is where they left themselves. A single-player pause, if the game ever wants one, is a `Standalone`-only freeze of the fixed clock and not a change to the input gate.

## Consequences

- One `RenderOrigin` per process. The server has no camera but has an origin, because the physics runs in `f32` relative to it (ADR 0002); with no `PrimaryObserver` it follows the first connected player. A second player fifty kilometres away is stepped in `f32` at that distance, which holds to a few millimetres and degrades linearly. Per-player physics frames or avian's `f64` feature would remove the limit; the choice is open in PLAN section 6.
- Intents ride a reliable ordered channel, so a lost packet stalls the player up to renet's resend interval rather than dropping a tick. An unreliable channel with the last few intents repeated in every packet is the MMO-grade choice and a contained change in the adapter.
- The client picks its own network id (epoch nanoseconds) and netcode runs unsecure; there is no token server and no account. A wrong `--seed` is logged, not refused, because the server does not replicate the seed: the client loads its world before it connects.
- Players collide with one another through the move and slide (kinematic capsules), which is why the server spreads spawns two metres apart, on the first slot nobody is standing on. Walking through other players or pushing them is a physics-crate decision.
- A new player is spawned a third of a metre over the ground, under the controller's snap distance, so the server's first step stands it there in one tick. A two-metre drop had the server's player landing over several ticks while the client, still building its collider, predicted it standing still, and every connect began with a correction.
- Remote players are drawn from the latest replicated position interpolated over one tick by the same `PreviousWorldPosition` the local player uses; a late update shows as a small hitch. A snapshot buffer with a render delay is the next step when it matters.
